# คู่มือเจ้าของ: สลับปฏิทินหลัก (Google Calendar)

คู่มือนี้สำหรับผู้ดูแลระบบ ใช้เมื่อต้องการย้ายข้อมูลคิวไปอยู่ในปฏิทินของบัญชี Google อื่น (เช่น ปฏิทิน "OR Queue" ของบัญชีใหม่) หรือต่ออายุ token หลังสลับแล้ว ไม่มี token, รหัสปฏิทิน หรือคีย์จริงในไฟล์นี้ ใช้ค่าตัวอย่างในวงเล็บ `<...>` แทน

## ก่อนเริ่ม (ทำก่อนข้อ 1)

- **ตรวจโควตา Blob ก่อน merge:** Vercel → Storage → Blob → Usage เทียบกับเพดานของแพ็กเกจ Hobby เพราะรุ่นนี้อ่าน Blob มากขึ้น (ดูหัวข้อถัดไป)
- **merge และ deploy รุ่นนี้ให้เสร็จก่อนข้อ 1** หน้า `/admin` ส่วนปฏิทินหลักมีเฉพาะในรุ่นนี้
- **ก่อนสลับครั้งแรก ตรวจว่าแอปใช้งานได้ปกติ** (ดูตารางและลงคิวได้ แปลว่า `GOOGLE_REFRESH_TOKEN` ใน Vercel ยังใช้ได้) การตรวจตัวอย่างและการสลับใช้ token นี้อ่านปฏิทินหลักเดิมเพื่อคัดลอก ถ้า token นี้หมดอายุ ตรวจตัวอย่างและสลับจะล้มเหลว ให้ต่ออายุตาม README ก่อน

## สิ่งที่เปลี่ยนตั้งแต่ deploy รุ่นนี้ (มีผลแม้ยังไม่เคยสลับ)

- การบันทึกลง Calendar ทุกครั้ง (ลงคิว สลับวัน แก้ ยกเลิก วันปิดรับคิว วัน OR Extra วันที่ staff ไม่ว่าง) อ่าน Blob ใหม่ 1 ครั้ง เพื่อตรวจล็อกและปฏิทินหลัก
- การดูข้อมูลจาก Calendar อ่าน Blob ไม่เกิน 1 ครั้งต่อ 30 วินาทีต่อ instance รวมแล้วจำนวนการอ่าน Blob ประมาณสองเท่าของเดิม
- ถ้า Blob ขัดข้องหรือหมดเวลา การเรียก Calendar จะตอบ HTTP 503 `อ่านการตั้งค่าปฏิทินไม่สำเร็จ กรุณาลองใหม่` (ไม่ย้อนไปใช้ค่าใน Vercel เอง) รวมถึง `nansurg7@gmail.com` ผู้ดูแลระบบหลักถาวร ที่ยังเข้าสู่ระบบได้ แต่ดูหรือแก้ตารางคิวไม่ได้ (การบันทึกล้มเหลวทันทีเพราะอ่านการตั้งค่าใหม่ทุกครั้ง การดูใช้ได้อีกไม่เกิน 30 วินาทีจาก cache)
- การบันทึกแต่ละครั้งต้องได้คำตอบแรกจาก Google ภายใน 30 วินาที (นับจากก่อนตรวจล็อก) ไม่เช่นนั้นแอปตัดคำขอและแจ้งให้ตรวจข้อมูลก่อนลองใหม่ (การลงคิวใหม่จะตรวจซ้ำเองว่าบันทึกไปแล้วหรือไม่) ส่วนการอ่านเนื้อหาคำตอบหลังจากนั้นไม่ถูกตัด
- การขอ access token ใหม่จาก Google มีเพดาน 10 วินาที (เดิมรอได้ไม่จำกัด) เกินแล้วแจ้งให้ลองใหม่
- ถ้า deploy แบบ Preview หรือ Development ใช้ Blob store เดียวกับ Production แต่ `CALENDAR_SETTINGS_KEY` ตั้งไว้เฉพาะ Production หลังสลับครั้งแรก การเรียก Calendar บน deploy เหล่านั้นจะได้ 503 (ใส่คีย์เดียวกันให้ Environment นั้น หรือให้ใช้ Blob store แยก)

## ภาพรวมที่ต้องรู้ก่อน

- **จนกว่าจะสลับครั้งแรก ระบบไม่เปลี่ยนที่เก็บข้อมูล** การเชื่อมปฏิทินใหม่ใน `/admin` เก็บไว้เป็น "ปฏิทินใหม่ที่เชื่อมไว้" เท่านั้น แอปยังใช้ `GOOGLE_CALENDAR_ID` และ `GOOGLE_REFRESH_TOKEN` จาก Vercel เหมือนเดิม และวิธีต่ออายุแบบเดิม (ใส่ refresh token ใหม่ใน Vercel แล้ว Redeploy) ยังใช้ได้
- **หลังสลับครั้งแรก** ปฏิทินหลักจะถูกบันทึกในไฟล์ตั้งค่าที่เข้ารหัสด้วย `CALENDAR_SETTINGS_KEY` ค่า `GOOGLE_REFRESH_TOKEN` ใน Vercel จะไม่ควบคุมปฏิทินอีกต่อไป (ดูหัวข้อ "ต่ออายุ token หลังสลับแล้ว")
- **ห้ามลบ `GOOGLE_REFRESH_TOKEN` ออกจาก Vercel** แม้สลับแล้ว: `auth.ts` ใช้การมีอยู่ของค่านี้ตัดสินว่าตอนเข้าสู่ระบบจะขอสิทธิ์ Calendar หรือไม่ (ถ้าลบ ทุกเครื่องจะถูกขอสิทธิ์ Calendar ตอนเข้าสู่ระบบและเก็บ token รายเครื่องอีก) และเป็นปฏิทินหลักสำรองถ้าไฟล์ตั้งค่าถูกลบ แค่อย่าแก้ค่านี้เพื่อต่ออายุหลังสลับแล้ว
- **การต่ออายุ token อย่างเดียวในโหมด env** (ยังไม่เคยสลับ แต่เชื่อมอีเมลและปฏิทินเดียวกับใน Vercel แล้วกดสลับ) ก็ย้ายปฏิทินหลักเข้าไฟล์ตั้งค่าเช่นกัน หลังจากนั้น `GOOGLE_REFRESH_TOKEN` ใน Vercel ไม่ควบคุมปฏิทินอีก
- ขณะสลับ ระบบ **หยุดการบันทึก (ลงคิว สลับวัน แก้ ยกเลิก) เป็นช่วง ๆ** ประกาศผู้ใช้เผื่อไว้ประมาณ 10–15 นาที (หน้าจอแจ้งไว้แล้ว) การดูตารางและค้นหายังใช้ได้ตามปกติ
- ปฏิทินที่ใช้อยู่เดิม **ไม่ถูกแก้ไขหรือลบ** และจะถูกบันทึกเป็น "ปฏิทินก่อนหน้า"
- สิทธิ์ Calendar ที่ใช้มีตัวเดียวคือ `calendar.events` (ตัวเดียวกับที่สคริปต์ token ขอ)
- เหตุการณ์ที่คัดลอกใช้รหัสเดิมเมื่อ Google รับรหัสนั้น (รายการที่ Google ไม่รับได้รหัสใหม่ ดูข้อถัดไป) และรายงานเวลารอยังใช้วันที่สร้าง/แก้ไขเดิมจาก `orig_created` / `orig_updated`
- **รายการที่ Google ไม่รับรหัสเดิม** (เช่น รายการเดิมที่พิมพ์เองหรือนำเข้าจากโปรแกรมอื่น) ระบบออกรหัสใหม่ให้อัตโนมัติ (รายการเดียวกันได้รหัสใหม่เดิมทุกครั้ง จึงกดสลับซ้ำได้โดยไม่เกิดรายการซ้ำ) และเก็บรหัสเดิมไว้ใน `orig_id` แอปยังอ่านรายการเหล่านี้ได้ตามปกติ ไม่ต้องทำอะไรและไม่ใช่เหตุให้หยุด (หน้าที่เปิดค้างไว้ก่อนสลับให้โหลดใหม่หลังสลับ)
- **รายการซ้ำ (recurring)** คัดลอกทั้งรายการต้นแบบและ **รายการยกเว้น** (วันที่ถูกย้าย/แก้ไข หรือถูกยกเลิกเฉพาะวันนั้น) ระบบดูปฏิทินแบบเดียวกับที่แอปเห็น (แตกรายการซ้ำเป็นทุกวัน) **ในช่วงตั้งแต่ 1 ม.ค. 2000 ถึงล่วงหน้า 400 วันนับจากวันที่กด** (แอปให้ลงคิวได้ถึงสิ้นเดือนที่ห่างจากเดือนปัจจุบัน 12 เดือน ซึ่งอยู่ในช่วงนี้ แต่หน้าตารางของ staff อ่านคิวที่จะมาถึงแบบไม่จำกัดวัน วันของรายการซ้ำที่ไกลเกิน 400 วันจึงอยู่นอกการตรวจ แม้จะถูกคัดลอกไปพร้อมรายการต้นแบบ) ถ้าวันใดของรายการซ้ำที่แอปอ่านได้ ระบบคัดลอกรายการซ้ำนั้นทั้งชุด ทุกอย่างที่แอปอ่านได้ในช่วงนี้ รวมถึงรายการยกเว้นที่แอปอ่านได้แต่ถูกย้ายออกนอกช่วง ต้องอยู่ในแผนคัดลอก ถ้ามีรายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอก ระบบจะปฏิเสธการสลับก่อนล็อก (แถว "รายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอก" ต้องเป็น 0) รายการนอกช่วงที่ไม่ได้เป็นส่วนของรายการซ้ำที่คัดลอก การตรวจขั้นสุดท้ายมองไม่เห็น
- ระบบใส่รายการยกเว้นหลังคัดลอกรายการต้นแบบเสร็จ: วันที่ถูกย้าย/แก้ไขเขียนด้วย PUT (ตามเอกสารของ Google) วันที่ถูกยกเลิกใช้ DELETE กับวันนั้น (พฤติกรรมที่ทดสอบกับ Google จริงแล้ว แต่ยังไม่มีเอกสารของ Google ยืนยัน รวมถึงรูปแบบรหัสของแต่ละวัน) จึงมี **การตรวจขั้นสุดท้าย** ก่อนสลับ: เทียบสิ่งที่แอปจะเห็นในปฏิทินใหม่กับปฏิทินหลักทั้งสองทาง (ทุกวันที่แอปอ่านได้ต้องมีครบ เนื้อหาตรงกัน และไม่มีวันเกิน) ถ้าไม่ตรง จะไม่สลับ (ปฏิทินหลักไม่เปลี่ยน) ถ้าส่งรายการต้นแบบซ้ำ ระบบใส่วันที่ถูกย้าย/แก้ไขของรายการนั้นใหม่ทุกครั้ง (Google ล้างวันเหล่านั้นเมื่อรายการต้นแบบถูกเขียนทับ)
- รายการยกเว้นที่ไม่ตรงกับวันใดของรายการซ้ำแล้ว (เช่น หลังแก้กฎการซ้ำ) แอปแสดงไม่ได้อยู่แล้ว ระบบไม่คัดลอกและนับไว้ในรายละเอียดสำหรับนักพัฒนา (ไม่บล็อก)

## ขั้นตอนสลับ (ตามลำดับ)

1. **สร้างคีย์ตั้งค่า** รัน `openssl rand -base64 32` ที่เทอร์มินัล
2. **ใส่ใน Vercel** เพิ่ม Environment Variable ชื่อ `CALENDAR_SETTINGS_KEY` ค่า = ผลจากข้อ 1 เลือก Environment = Production และติ๊ก **Sensitive** แล้ว **Redeploy** เก็บสำเนาคีย์ไว้ในโปรแกรมจัดการรหัสผ่านของเจ้าของ ห้ามใส่ในโค้ดหรือ commit (ถ้าคีย์หาย ดูหัวข้อ "คีย์หาย")
3. **ขอ refresh token ของบัญชีใหม่** ที่โฟลเดอร์รากของโปรเจกต์ (repo) รัน
   `node --env-file=.env.local scripts/get-calendar-refresh-token.mjs --email <new-account@example.com>`
   เงื่อนไขก่อนรัน:
   - `.env.local` ต้องมี `AUTH_GOOGLE_ID` และ `AUTH_GOOGLE_SECRET` ของ **OAuth client ตัวเดียวกับที่ Vercel Production ใช้** (token ผูกกับ client ที่ขอ ใช้กับ client อื่นไม่ได้)
   - OAuth client นั้นต้องลงทะเบียน redirect URI `http://localhost:3000/api/auth/callback/google`
   - พอร์ต 3000 ต้องว่าง (หยุด `npm run dev` ก่อน)
   - consent screen (Google Auth Platform → Audience) ต้องเป็น **In production** ถ้ายังเป็น Testing token จะหมดอายุใน 7 วัน
   - เปิดลิงก์ที่แสดงแล้วเข้าสู่ระบบด้วยบัญชีตาม `--email` เท่านั้น ถ้าเข้าด้วยบัญชีอื่น สคริปต์จะแจ้ง `Signed in as <อีเมลที่เข้า>, expected <อีเมลที่สั่ง>` และไม่พิมพ์ token
   - บัญชีที่ไม่ใช่เจ้าของแอปอาจเห็นหน้า "Google hasn't verified this app" ให้เลือก Advanced → Continue (ข้อนี้ **ยังไม่ได้ยืนยัน** กับบัญชีที่ไม่ใช่เจ้าของแอป ถ้ากดผ่านไม่ได้ให้หยุดและแจ้งผู้พัฒนา)
   - บัญชีต้องมี **สิทธิ์เขียน** ในปฏิทินปลายทาง ("Make changes to events") ไม่จำเป็นต้องเป็นเจ้าของ
   สคริปต์พิมพ์ token ที่เทอร์มินัลเท่านั้น ไม่เขียนลงไฟล์
4. **ตั้ง time zone ของปฏิทินใหม่ แล้วเชื่อมที่ `/admin`** ก่อนเชื่อม เปิด Google Calendar → Settings → เลือกปฏิทินใหม่ → Time zone ตั้งเป็น **(GMT+07:00) Bangkok** (หลังสลับ แอปอ่านปฏิทินใหม่ตาม time zone ของปฏิทินนั้นเอง ถ้าเป็นโซนอื่น เคสที่มีเวลาจะแสดงผิดวันหรือผิดเวลา ระบบจึงตรวจ time zone ของปฏิทินใหม่ก่อนล็อก ทั้งตอนตรวจตัวอย่างและตอนกดสลับ ถ้าไม่ใช่ (GMT+07:00) Bangkok หรือ Google ไม่ส่งค่ามา จะไม่ให้สลับและบอกวิธีแก้ ปฏิทินหลักปัจจุบันก็ต้องเป็น (GMT+07:00) Bangkok เช่นกัน ดูข้อ 5) จากนั้นในส่วน "ปฏิทินหลัก (Google Calendar)" กรอกอีเมล Google ของปฏิทินใหม่, รหัสปฏิทิน (calendar id) และ refresh token แล้วกด "เชื่อมต่อปฏิทินใหม่" (ขั้นนี้ยังไม่เปลี่ยนปฏิทินหลัก)
   - รหัสปฏิทินหาได้ที่ Google Calendar → Settings → เลือกปฏิทินนั้น → Integrate calendar → **Calendar ID**
   - ตอนเชื่อม ระบบตรวจแค่สิทธิ์อ่าน (อ่านรายการ event ได้) ถ้าบัญชีมีสิทธิ์แค่ดู การเชื่อมจะผ่าน แต่การคัดลอกจะล้มเหลวตอนกดสลับ
5. **ตรวจตัวอย่าง** กด "ตรวจตัวอย่างก่อนสลับ" แล้วดูตัวเลขให้ครบ: จำนวนข้อมูลที่จะคัดลอกแต่ละประเภท, "ข้ามไป", "รายการซ้ำ (recurring)", "รายการในปฏิทินปลายทางที่ปฏิทินหลักไม่มีแล้ว", "รหัส event ที่ต้องออกรหัสใหม่ (ไม่บล็อก)", "รายการยกเว้นของรายการซ้ำที่จะคัดลอก" และ "รายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอก"
   - ระบบตรวจ time zone ของปฏิทินใหม่ก่อนล็อก ถ้าหน้าจอแจ้งว่าปฏิทินใหม่ไม่ได้ตั้ง time zone เป็น (GMT+07:00) Bangkok ให้แก้ตามข้อ 4 แล้วกดตรวจตัวอย่างใหม่ (ไม่ต้องติดต่อผู้พัฒนา)
   - ระบบตรวจ time zone ของปฏิทินหลักปัจจุบันด้วย (ต้องเป็น (GMT+07:00) Bangkok เพราะแอปแสดงวันและเวลาของคิวตาม time zone ของปฏิทินหลัก) ถ้าหน้าจอแจ้งว่าปฏิทินหลักปัจจุบันไม่ได้อยู่ในเวลาไทยหรือตรวจไม่ได้ การสลับจะถูกบล็อก ให้หยุด **ห้ามเปลี่ยน time zone ของปฏิทินหลักปัจจุบันเอง** (คิวที่มีเวลาจะเลื่อนทันที) และติดต่อผู้พัฒนา
   - สัญญาณที่ห้ามสลับ: "รายการในปฏิทินปลายทางที่ปฏิทินหลักไม่มีแล้ว" (conflicts) ต้องเป็น 0, "รายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอก" ต้องเป็น 0 และหน้าจอต้องไม่แสดงข้อความปฏิเสธจากแผนการคัดลอก (ถ้ามี หน้าจอจะไม่ให้กดสลับและบอกเหตุผล)
   - ถ้า conflicts มากกว่า 0 **ห้ามสลับเข้าปฏิทินนั้น** ให้สร้างปฏิทินใหม่ที่ว่างแทน (แล้วเริ่มจากข้อ 3 ใหม่) รายการยกเว้นของรายการซ้ำในปลายทางที่ปฏิทินหลักไม่มีก็นับเป็น conflicts ด้วย
   - ถ้าหน้าจอแสดงข้อความปฏิเสธจากแผนการคัดลอก (เช่น รหัสใหม่ซ้ำกัน รายการยกเว้นของรายการซ้ำที่ระบบคัดลอกไม่ได้ หรือมีรายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอก) ให้หยุด **ห้ามแก้ไขหรือลบรายการใด ๆ ใน Google Calendar** (จะทำให้ข้อมูลการจองหาย) และติดต่อผู้พัฒนา
   - "รหัส event ที่ต้องออกรหัสใหม่ (ไม่บล็อก)" เป็นข้อมูลเท่านั้น ระบบคัดลอกรายการเหล่านั้นด้วยรหัสใหม่ให้เอง (รหัสเดิมเก็บใน `orig_id`)
   - คำเตือน "ปฏิทินปลายทางไม่ว่าง" เป็นเรื่องปกติและคาดไว้เมื่อ **ทำต่อหลังคัดลอกไปบางส่วน** (ตัวอย่างไม่ถูกเก็บไว้ ต้องกดตรวจตัวอย่างใหม่หลังโหลดหน้าซ้ำ) และเมื่อสลับกลับไปปฏิทินจาก env ถ้า conflicts เป็น 0 และไม่มีข้อความปฏิเสธ ก็สลับต่อได้ คำเตือนนี้อย่างเดียวไม่ใช่เหตุให้หยุด
   - ถ้าตัวเลขอื่นไม่ตรงกับที่คาด หรือปลายทางไม่ใช่ปฏิทินที่ถูกต้อง อย่าสลับ
6. **ประกาศช่วงหยุดบันทึก** แจ้งผู้ใช้ทุกคนว่าจะลงคิวไม่ได้เป็นช่วง ๆ ประมาณ 10–15 นาที และห้ามปิดหน้า `/admin` ระหว่างสลับ
7. **กดสลับ** แล้วกด "ยืนยันสลับปฏิทิน" รอจนหน้าจอแจ้งผล
   - ก่อนล็อก ระบบตรวจซ้ำแบบเดียวกับข้อ 5 (conflicts และรายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอกต้องเป็น 0 และแผนการคัดลอกต้องไม่ถูกปฏิเสธ คำเตือนปลายทางไม่ว่างและรหัสที่ต้องออกใหม่ไม่ใช่เหตุปฏิเสธ) ถ้าพบรายการที่ห้ามสลับ จะปฏิเสธทันทีโดยไม่หยุดการบันทึก
   - ถ้าหน้าจอแจ้งว่าปฏิทินใหม่ไม่รับรายการยกเว้นของรายการซ้ำบางรายการ (ไม่พบวันนั้นในรายการซ้ำ) การกดซ้ำไม่ช่วย ให้หยุดและติดต่อผู้พัฒนา ปฏิทินหลักยังไม่เปลี่ยน
   - ถ้าการตรวจขั้นสุดท้ายไม่ผ่าน หน้าจอจะแจ้งว่าข้อมูลในปฏิทินใหม่ไม่ตรงกับปฏิทินหลัก ปฏิทินหลักยังไม่เปลี่ยน กดสลับอีกครั้งได้หนึ่งครั้ง ถ้ายังไม่ผ่านให้หยุดและติดต่อผู้พัฒนา
   - การอ่านแต่ละรอบรวมการอ่านแบบที่แอปเห็น (ทุกวันของรายการซ้ำ) ด้วย ซึ่งใช้เวลาเพิ่ม ถ้าอ่านไม่ทันในเวลาของรอบ หน้าจอจะบอกให้กดสลับอีกครั้ง (ปลอดภัย ไม่สลับครึ่งทาง)
   - แต่ละรอบที่กด: คัดลอกได้สูงสุด 150 วินาที จากนั้นรอ 45 วินาที (นับจากตอนล็อก) ให้การบันทึกที่ค้างอยู่เสร็จ อ่านข้อมูลซ้ำและตรวจ (ทุกอย่างก่อนสลับต้องเสร็จภายใน 170 วินาที) สลับปฏิทินหลัก แล้วล็อกต่ออีก 35 วินาทีก่อนปลดล็อก รวมแล้วไม่เกินราว 4.5 นาทีต่อรอบ และแม้ปฏิทินเล็กมากก็ใช้ราว 1.5 นาที
   - ปฏิทินใหญ่อาจต้องกดสลับหลายรอบ ถ้าหน้าจอบอกให้กดสลับอีกครั้ง ให้กดต่อ รอบถัดไปข้าม event ที่คัดลอกแล้ว การหยุดบันทึกไม่ต่อเนื่องระหว่างรอบ (ปลดล็อกระหว่างรอบ) รอบถัดไปจะอ่านข้อมูลที่เพิ่มหรือแก้ระหว่างรอบซ้ำให้เอง แต่ถ้ามีการยกเลิกหรือลบรายการในปฏิทินหลักระหว่างรอบ รอบถัดไปจะถูกปฏิเสธ (ปลายทางมีรายการที่ปฏิทินหลักไม่มีแล้ว) ให้สร้างปฏิทินใหม่ที่ว่าง แล้วเริ่มจากข้อ 3 ใหม่
8. **ตรวจว่าตารางเหมือนเดิม** เปิดหน้าตาราง ดูหลายเดือน เทียบจำนวนเคส วันปิดรับคิว วัน OR Extra และวันที่ staff ไม่ว่าง และสุ่มดูว่าเคสที่มีเวลาอยู่วันเดิมเวลาเดิม (ปฏิทินใหม่ต้องเป็น (GMT+07:00) Bangkok ตามข้อ 4)
9. **แจ้งทุกคน: ห้ามแก้ในปฏิทินโดยตรง** ให้ลงคิว แก้ ยกเลิก และจัดการวันต่าง ๆ ผ่านแอปเท่านั้น (ห้ามแก้ใน Google Calendar โดยตรง)

## ปลดล็อก

ระหว่างสลับระบบล็อกการสลับไว้ ล็อกหมดอายุเองใน 20 นาที ถ้าหน้า `/admin` แสดงว่าล็อกค้างและแน่ใจว่าไม่มีการสลับกำลังทำงานอยู่ จึงกด "ปลดล็อก" **ห้ามกดปลดล็อกขณะที่การสลับยังทำงานอยู่** เพราะอาจตัดการสลับให้ขาดกลางคัน (ถ้าล็อกเพิ่งเกิดไม่ถึง 1 นาที ระบบให้ติ๊กยืนยันก่อน) หลังสลับเสร็จระบบยังคงล็อกต่ออีกประมาณ 35 วินาที เป็นเรื่องปกติ

## ต่ออายุ token หลังสลับแล้ว

หลังสลับครั้งแรก (และหลังย้อนกลับด้วยการสลับ เพราะปฏิทินหลักยังอยู่ในไฟล์ตั้งค่า) การแก้ `GOOGLE_REFRESH_TOKEN` ใน Vercel **ไม่มีผลต่อปฏิทิน** ถ้า token ของปฏิทินหลักหมดอายุหรือถูกเพิกถอน (หน้าแอปแจ้ง 503 ว่าการเชื่อมหมดอายุ):

1. รันสคริปต์ในข้อ 3 อีกครั้งด้วย `--email` ของบัญชีปฏิทินหลักปัจจุบัน
2. ที่ `/admin` เชื่อมอีเมลและรหัสปฏิทินเดิมซ้ำกับ token ใหม่
3. กดตรวจตัวอย่าง จะแจ้งว่าเป็นการต่ออายุ token เท่านั้น แล้วกดสลับ ระบบเปลี่ยนเฉพาะ token ที่เก็บไว้ **ไม่คัดลอกข้อมูลและไม่หยุดการบันทึกนาน**

## คีย์หาย (`CALENDAR_SETTINGS_KEY`)

- **ก่อนสลับครั้งแรก** (ไฟล์ตั้งค่ายังไม่มีปฏิทินหลัก) แอปยังใช้ค่าใน Vercel ตามปกติ ใส่คีย์ใหม่ Redeploy แล้วเชื่อมปฏิทินใหม่ซ้ำ
- **หลังสลับครั้งแรก** token ที่เก็บไว้ถอดรหัสไม่ได้ การเรียก Calendar ทั้งหมดตอบ 503 `อ่านการตั้งค่าปฏิทินไม่สำเร็จ` วิธีแก้: ใส่คีย์เดิมกลับ หรือถ้าคีย์หายจริง สร้างคีย์ใหม่ (ข้อ 1–2) แล้วขอ token ใหม่ของ **อีเมลและปฏิทินหลักปัจจุบัน** (ข้อ 3) เชื่อมที่ `/admin` ตรวจตัวอย่าง (จะแจ้งว่าต่ออายุ token เท่านั้น) แล้วกดสลับ ระบบจะเก็บ token ใหม่ด้วยคีย์ใหม่
- **อย่าแก้ด้วยการเชื่อมปฏิทินอื่น** การคัดลอกต้องเปิด token ของปฏิทินหลักปัจจุบัน ซึ่งเปิดไม่ได้แล้ว จะล้มเหลวที่ขั้นเปิด token

## Rollback (ย้อนกลับ)

**กฎ: ย้อนกลับ = สลับไปปฏิทินใหม่ที่ว่าง** (ในบัญชีก่อนหน้าหรือบัญชีใดก็ได้) **ห้ามสลับกลับไปปฏิทินเดิมที่มีข้อมูลอยู่แล้ว** ถ้าหลังการสลับมีการยกเลิกหรือลบรายการใด ๆ (ยกเลิกเคส ลบวันปิดรับคิว วัน OR Extra หรือวันที่ staff ไม่ว่าง) เพราะแอปลบรายการเหล่านั้นออกจากปฏิทินหลักจริง แต่ปฏิทินเดิมยังมีอยู่ ถ้าสลับกลับ รายการที่ยกเลิกแล้วจะกลับมาในแอป

- คำเตือน "ปฏิทินปลายทางไม่ว่าง" ตอนตรวจตัวอย่างเป็นเรื่องปกติเมื่อปลายทางคือปฏิทินเดิม ไม่ใช่เหตุให้หยุดด้วยตัวเอง ให้ดูแถว conflicts แถวรายการที่แอปแสดงแต่ไม่อยู่ในแผนคัดลอก และข้อความปฏิเสธบนหน้าจอ (ข้อ 5) ถ้าปฏิทินเดิมมีรายการที่ปฏิทินหลักปัจจุบันไม่มีแล้ว (conflicts มากกว่า 0) **อย่าสลับไปที่นั่น** หน้าจอจะไม่ให้กดสลับ และเซิร์ฟเวอร์จะปฏิเสธก่อนล็อก (ไม่หยุดการบันทึก)
- ขั้นตอน: สร้างปฏิทินใหม่ที่ว่างในบัญชีที่ต้องการ ตั้ง time zone เป็น (GMT+07:00) Bangkok (อีเมลและรหัสของปฏิทินก่อนหน้าดูได้ที่แถว "ปฏิทินก่อนหน้า" ในหน้า `/admin`) → ขอ token (ข้อ 3) → เชื่อม (ข้อ 4) → ตรวจตัวอย่างว่า conflicts เป็น 0 และไม่มีข้อความปฏิเสธ (ข้อ 5 ปลายทางที่สร้างใหม่ควรว่างด้วย) → สลับ (ข้อ 6–9)
- หลังย้อนกลับ ปฏิทินหลักยังอยู่ในไฟล์ตั้งค่า (สถานะแสดงว่าไม่ได้ "ตั้งต้นจาก env") การต่ออายุ token ยังทำที่ `/admin` ตามหัวข้อ "ต่ออายุ token หลังสลับแล้ว"

**การลบไฟล์ตั้งค่า = ทางฉุกเฉินที่สูญข้อมูลเท่านั้น** แอปจะกลับไปใช้ปฏิทินจาก Vercel ทันที แต่การยกเลิกและการแก้ไขที่ทำหลังการสลับจะย้อนกลับ (เคสที่ยกเลิกไปแล้วจะกลับมาเป็นคิวที่ยังจองอยู่) และรายการที่สร้างหลังการสลับจะหายไปจากแอป

**ห้าม rollback โค้ด (promote deployment รุ่นก่อนรุ่นนี้) หลังสลับครั้งแรก** โค้ดรุ่นเก่าไม่รู้จักไฟล์ตั้งค่า จะใช้ `GOOGLE_CALENDAR_ID` / `GOOGLE_REFRESH_TOKEN` จาก Vercel ทันทีโดยไม่มีคำเตือน ข้อมูลแยกเป็นสองที่ (การบันทึกใหม่ไปที่ปฏิทินเก่า ส่วนข้อมูลหลังการสลับอยู่ในปฏิทินหลักปัจจุบัน) ก่อน promote ต้องให้ปฏิทินที่โค้ดเก่าจะใช้เป็นปฏิทินหลักปัจจุบันก่อน: สลับกลับไปปฏิทินจาก env (ทำได้เฉพาะเมื่อหน้าจอยอมให้สลับ) หรือยอมรับการสูญข้อมูล คำเตือนเรื่องสิทธิ์ viewer ก่อน rollback โค้ด (README หัวข้อ "สิทธิ์ผู้ใช้ดูอย่างเดียว (viewer)") ยังใช้ตามเดิม

## ข้อควรระวัง

- ห้ามแก้ในปฏิทินโดยตรง หลังสลับ ให้แก้ผ่านแอปเท่านั้น
- ปฏิทินสำเนาเพิ่มเติม (phase C) ไม่รวมในรุ่นนี้
- ห้ามใส่ token, คีย์ หรือรหัสปฏิทินจริงลงในไฟล์ใด ๆ ในโค้ด
