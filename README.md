# Operative Schedule

ระบบลงคิวผ่าตัด Breast & Endocrine Surgery CMU สำหรับ OR 17 และ OR Extra โดยใช้ Google Calendar ของ `hnbcmu@gmail.com` เป็นแหล่งข้อมูลกลาง

## กติกาหลัก

- ผู้ใช้งานและผู้บันทึกคิวต้องเข้าสู่ระบบด้วยบัญชี Google ที่อยู่ในรายชื่อผู้ใช้ที่ได้รับอนุญาตและเปิดใช้งานอยู่ (ดู “ผู้ใช้และสิทธิ์” ด้านล่าง)
- OR 17 เปิดวันอังคารและพฤหัสบดี สูงสุด 4 เคสต่อวัน และต้องมี Cancer อย่างน้อย 1 เคส
- OR Extra เปิดเป็นรายวันในวันจันทร์หรือพฤหัสบดี และรับเฉพาะ Cancer
- Cancer เลือกคิวว่างเร็วที่สุดอัตโนมัติ หรือระบุวันเองได้
- บันทึกเคสและวัน Extra ลง Google Calendar ทันที
- ค้นหาเคสย้อนหลังจาก HN ชื่อ หรือสกุล แล้วสลับไปยังคิวที่ยังว่างได้
- เก็บการสลับวันไว้ในกิจกรรม Google Calendar และแสดง 10 เคสล่าสุดในหน้าเว็บ
- ผู้ดูแลเพิ่ม แก้ไข ค้นหา และลบวันปิดรับคิวได้จากแท็บ “วันปิดรับคิว” โดยปิดทั้ง OR 17 และ OR Extra
- หากวันที่ปิดมีคิวเดิม ระบบจะแสดงรายการให้ยืนยันและคงคิวเดิมไว้ แต่ห้ามสร้างหรือย้ายคิวใหม่เข้าวันนั้น
- ทุกเคสใหม่ต้องระบุ **ระยะเวลาผ่าตัด** เป็นจำนวนนาที (จำนวนเต็ม 1–360) และผลรวมระยะเวลาของเคสในห้องเดียวกันวันเดียวกันต้องไม่เกิน **360 นาที** (OR 17 และ OR Extra นับแยกกัน) ถ้าการลงคิว สลับวัน หรือแก้ระยะเวลาทำให้เกิน 360 ระบบจะแสดงหน้าต่างแจ้งและปฏิเสธ แม้วันนั้นจะมีไม่ถึง 4 เคส
- วัน-ห้องที่มีเคสใดเคสหนึ่งไม่มีระยะเวลา (เคสที่ลงไว้ก่อนเริ่มใช้กฎนี้) จะไม่ถูกตรวจกฎ 360 นาที เคสเก่าที่ไม่มีระยะเวลาต้องระบุระยะเวลาเมื่อสลับวัน ส่วนการย่อระยะเวลา ย้ายออกจากวัน หรือเพิ่มระยะเวลาครั้งแรกให้เคสเก่าทำได้เสมอ
- แก้ระยะเวลาของเคสที่ลงแล้วได้จากผลการค้นหา (เฉพาะเคสวันนี้หรืออนาคต) ส่วนกิจกรรมเก่าที่คีย์ตรงใน Google Calendar ให้สลับวันแทน
- เปิดปฏิทินและลงคิวได้ถึงสิ้นเดือนที่ห่างจากเดือนปัจจุบัน 12 เดือน โดยแสดงปี พ.ศ. และเก็บวันที่เป็น ISO ค.ศ.

## การใช้งานบนมือถือและแท็บเล็ต

บนหน้าจอกว้างไม่เกิน 1000px ระบบแสดงทีละหน้าจอ และมีแถบเมนูด้านล่าง 4 หน้า: **ตาราง** (`?tab=schedule`), **ลงคิว** (`?tab=book`), **ค้นหา** (`?tab=search`) และ **แจ้งเตือน** (`?tab=alerts`) ตัวเลขบนแจ้งเตือนคือการสลับวันที่ยังไม่ได้ดูบนเครื่องนี้ (เก็บใน localStorage ของเบราว์เซอร์) ส่วนปุ่ม Sync, Export และออกจากระบบอยู่ในปุ่ม "เมนู" ด้านบน หน้าจอเดสก์ท็อปแสดงทุกส่วนพร้อมกันเหมือนเดิม

## ผู้ใช้และสิทธิ์

- รายชื่อผู้ใช้ที่ได้รับอนุญาต (อีเมล สิทธิ์ ผู้ใช้ / ดูอย่างเดียว / ผู้ดูแลระบบ และสถานะใช้งาน/ปิดชั่วคราว) เก็บเป็นไฟล์ JSON ใน Vercel Blob แบบ private (`or-queue/users.json`) ไม่ได้เขียนไว้ในโค้ด
- ผู้ดูแลระบบเพิ่ม แก้สิทธิ์ ปิดชั่วคราว และลบผู้ใช้ได้ที่หน้า `/admin` (เมนู “จัดการผู้ใช้” แสดงเฉพาะผู้ดูแลระบบ) การเปลี่ยนแปลงมีผลกับทุกเครื่องภายในประมาณ 30 วินาที
- `nansurg7@gmail.com` เป็นผู้ดูแลระบบหลักถาวร แก้ไขหรือลบไม่ได้
- `hnbcmu@gmail.com` เป็นเจ้าของ Google Calendar ของระบบ และเป็นผู้ใช้ตั้งต้นในรายชื่อ (ผู้ดูแลระบบปิดหรือลบได้เหมือนผู้ใช้อื่น)
- ถ้ายังไม่มีไฟล์รายชื่อ ระบบจะสร้างให้ครั้งแรกด้วยสองบัญชีข้างต้น ถ้าอ่านไฟล์รายชื่อไม่ได้ (Blob ขัดข้อง หมดเวลา หรือไฟล์เสีย) ระบบจะปฏิเสธทุกบัญชีชั่วคราว ยกเว้น `nansurg7@gmail.com` ที่ยังเข้าสู่ระบบได้

### สิทธิ์ผู้ใช้ดูอย่างเดียว (viewer)

- ผู้ใช้สิทธิ์ `viewer` (ดูอย่างเดียว) เข้าสู่ระบบ ดูตารางคิว ค้นหา และเปิดรายละเอียดเคสได้ แต่ลงคิว สลับวัน แก้ระยะเวลา ยกเลิกเคส กำหนดหรือยกเลิกวัน OR Extra หรือจัดการวันปิดรับคิว/วันที่ staff ไม่ว่างไม่ได้ (เซิร์ฟเวอร์ตอบ 403) แท็บ “ลงคิว” บนมือถือและแผงลงคิวบนจอกว้างจะไม่แสดง และลิงก์ `?tab=book` จะเปิดหน้า “ตาราง” แทน
- ผู้ดูแลระบบกำหนดสิทธิ์นี้ที่หน้า `/admin` โดยเลือก “ดูอย่างเดียว (viewer)” ตอนเพิ่มผู้ใช้หรือเปลี่ยนสิทธิ์ ผู้ใช้ใหม่ยังมีสิทธิ์ตั้งต้นเป็น `user`
- **คำเตือนก่อน rollback:** โค้ดเวอร์ชันเก่าไม่รู้จักสิทธิ์ `viewer` และจะอ่านเป็น `user` (ลงคิวได้) ก่อนย้อนกลับไปเวอร์ชันก่อนมีสิทธิ์นี้ มี 3 ทางเลือก: (1) ลบผู้ใช้ viewer ทุกคนออกจากรายชื่อที่หน้า `/admin` (2) **ปิดการใช้งาน** (deactivate) ผู้ใช้ viewer ทุกคนที่หน้า `/admin` ซึ่งย้อนกลับได้ โค้ดเก่าจะยังถือว่าบัญชีที่ปิดอยู่เป็นปิดเหมือนเดิม และเมื่อเปิดใช้งานกลับค่อยตั้งสิทธิ์ใหม่ หรือ (3) ยอมรับว่าคนเหล่านั้นจะกลายเป็นผู้ที่เขียนได้ ข้อควรระวัง: เมื่อผู้ดูแลระบบแก้รายชื่อครั้งถัดไปด้วยโค้ดเก่า โค้ดเก่าจะบันทึกสิทธิ์ที่ถูกอ่านเป็น `user` ลงไฟล์รายชื่อ ผู้ใช้ viewer เดิมจึงยังเป็นผู้ที่เขียนได้ต่อไป แม้จะ deploy เวอร์ชันใหม่กลับมาแล้ว ต้องตั้งสิทธิ์ viewer ใหม่ที่หน้า `/admin`

## ตั้งค่า

สร้าง `.env.local` จาก `.env.example` แล้วกำหนด Google OAuth Web Client และ `BLOB_READ_WRITE_TOKEN` (token ของ Vercel Blob store ที่เก็บรายชื่อผู้ใช้ ต้องมีทั้งเครื่องพัฒนาและ Vercel ห้าม commit):

```bash
cp .env.example .env.local
npm install
npm run dev
```

Authorized redirect URI สำหรับเครื่องพัฒนา:

`http://localhost:3000/api/auth/callback/google`

สำหรับ Vercel ให้เพิ่ม URI ของโดเมนจริง:

`https://<your-domain>/api/auth/callback/google`

## การเชื่อม Google Calendar (token ฝั่งเซิร์ฟเวอร์)

เมื่อตั้ง `GOOGLE_REFRESH_TOKEN` เซิร์ฟเวอร์จะถือสิทธิ์เข้าถึง Calendar ของ `hnbcmu@gmail.com` เพียงชุดเดียวและต่ออายุเอง ทุกเครื่องใช้ร่วมกัน การเข้าสู่ระบบจึงใช้พิสูจน์ตัวตนเท่านั้น (ไม่ขอสิทธิ์ Calendar และไม่สร้าง refresh token ต่อเครื่องอีก) ถ้าไม่ได้ตั้งค่านี้ ระบบจะใช้ token ใน cookie ของแต่ละเครื่องเหมือนเดิม ซึ่งหมดอายุเป็นรายเครื่องได้ (`Token has been expired or revoked`)

ตั้งค่าครั้งแรก ตามลำดับ:

1. Google Cloud Console → Google Auth Platform → Audience: เปลี่ยน Publishing status เป็น **In production** ถ้ายังเป็น Testing refresh token จะหมดอายุทุก 7 วัน และทุกเครื่องจะพังพร้อมกัน (จะเห็นหน้า "Google hasn't verified this app" ให้เลือก Advanced → Continue ซึ่งใช้ได้กับบัญชีเจ้าของแอปเอง)
2. หยุด `npm run dev` แล้วรัน `node --env-file=.env.local scripts/get-calendar-refresh-token.mjs` เปิดลิงก์ที่แสดง เข้าสู่ระบบด้วย `hnbcmu@gmail.com` สคริปต์จะพิมพ์ refresh token ที่เทอร์มินัลเท่านั้น ไม่เขียนลงไฟล์
3. ตั้งค่าเป็น Environment Variable `GOOGLE_REFRESH_TOKEN` ใน Vercel (Production) แล้ว Redeploy ห้าม commit token
4. ทดสอบเปิดแอปจากเครื่องที่เคยขึ้น error

ถ้าแอปแสดง "การเชื่อม Google Calendar ของระบบหมดอายุหรือถูกเพิกถอน ผู้ดูแลระบบต้องต่ออายุ" (HTTP 503) ให้ทำข้อ 2–3 ซ้ำ (ใช้ได้จนกว่าจะสลับปฏิทินหลักครั้งแรก ดูหัวข้อ "ปฏิทินหลักและการสลับ" ด้านล่าง) การเข้าสู่ระบบใหม่บนเครื่องผู้ใช้ไม่ช่วยในโหมดนี้ สาเหตุที่พบบ่อยคือเปลี่ยนรหัสผ่านบัญชี Google, กดเพิกถอนสิทธิ์แอปที่ myaccount.google.com/permissions หรือ consent screen กลับไปเป็น Testing

## ปฏิทินหลักและการสลับ

ผู้ดูแลระบบสลับ **ปฏิทินหลัก** (Google Calendar ที่เป็นที่เก็บข้อมูลของแอป) ได้ที่หน้า `/admin` ขั้นตอนเต็มและ rollback อยู่ใน [`docs/owner-pack/calendar-switch-RUNBOOK.md`](docs/owner-pack/calendar-switch-RUNBOOK.md)

- **ตัวแปรใหม่ `CALENDAR_SETTINGS_KEY`:** คีย์เข้ารหัสไฟล์ตั้งค่าปฏิทิน สร้างด้วย `openssl rand -base64 32` ใส่ใน Vercel เป็น Production + Sensitive แล้ว Redeploy เก็บสำเนาในโปรแกรมจัดการรหัสผ่าน ห้ามใส่ในโค้ด ถ้าคีย์หายหรือเปลี่ยน token ที่เก็บไว้ถอดรหัสไม่ได้ แอปจะปิดการเรียก Calendar ด้วย 503 `อ่านการตั้งค่าปฏิทินไม่สำเร็จ`
- **จนกว่าจะสลับครั้งแรก:** การเชื่อมปฏิทินใหม่เก็บเป็นตัวเลือกเท่านั้น แอปยังใช้ `GOOGLE_CALENDAR_ID` / `GOOGLE_REFRESH_TOKEN` จาก Vercel และขั้นตอนต่ออายุด้านบนยังใช้ได้
- **หลังสลับครั้งแรก:** ปฏิทินหลักอยู่ในไฟล์ตั้งค่า `GOOGLE_REFRESH_TOKEN` ใน Vercel ไม่ควบคุมปฏิทินอีก การต่ออายุ token ของบัญชีเดิมทำโดยเชื่อมอีเมลและปฏิทินเดิมซ้ำที่ `/admin` แล้วกดสลับ (เปลี่ยนเฉพาะ token ไม่คัดลอกข้อมูล) อย่าแก้ Vercel env เพื่อต่ออายุอีก
- สคริปต์ token รับ `--email <address>` เพื่อขอ token ของบัญชีใดก็ได้ (ค่าเริ่มต้น `hnbcmu@gmail.com`) ใช้สิทธิ์ `calendar.events` อย่างเดียว
- ขณะสลับ การบันทึกถูกหยุดประมาณ 10–15 นาที (ดูได้ตามปกติ) ล็อกค้างหมดอายุเองใน 20 นาที ปุ่ม "ปลดล็อก" ห้ามกดขณะที่การสลับยังทำงาน ปฏิทินเดิมไม่ถูกแก้หรือลบ
- หลังสลับ ทุกคนต้องแก้ข้อมูลผ่านแอปเท่านั้น ห้ามแก้ใน Google Calendar โดยตรง

## วันที่ staff ไม่ว่าง

บันทึกช่วงวันที่ staff แต่ละคนไม่ว่าง (เต็มวัน ไม่มีครึ่งวัน) จัดการได้ในแท็บเดียวกับ **วันปิดรับคิว** เลือก staff ได้หลายคนในครั้งเดียว ระบบจะสร้างรายการแยกต่อคน เก็บเป็น all-day event บน Google Calendar ของ `hnbcmu@gmail.com` (แสดงเป็น "{staff} ไม่ว่าง") วันที่ที่เลือกได้คือตั้งแต่วันนี้ถึงสิ้นสุดช่วง 12 เดือนข้างหน้า และช่วงวันที่ของ staff คนเดียวกันซ้อนกันไม่ได้

- จองหรือสลับวันถูกปฏิเสธ **เฉพาะเมื่อ staff ทุกคนในเคสนั้นไม่ว่าง** วันนั้นจะเป็นสีเทา กดไม่ได้ พร้อมเหตุผล ส่วนวันนั้นของเคสอื่นยังจองได้ตามปกติ
- ถ้าไม่ว่างเพียงบางคนในเคส ยังจองหรือสลับได้ แต่แสดงคำเตือนว่าใครไม่ว่าง (staff ในเคสไม่ถูกแก้)
- เคสที่จองไว้แล้วจะไม่ถูกย้ายหรือลบอัตโนมัติ ถ้ามี staff คนใดในเคสไม่ว่างในวันของเคส เคสจะมีป้าย **ควรย้ายวัน** จนกว่าจะย้ายเคสหรือลบรายการไม่ว่าง และตอนบันทึกจะมีหน้าต่างยืนยันแสดงเคสที่ได้รับผลกระทบ
- กฎบังคับที่เซิร์ฟเวอร์ทั้งตอนจอง ตอนสลับวัน และตรวจซ้ำหลังเขียน หน้าเว็บที่เปิดค้างไว้ก่อนหน้านี้จึงจองวันที่ถูกบล็อกไม่ได้ และถ้าอ่าน Calendar ไม่ได้ ระบบจะปฏิเสธการจองแทนที่จะปล่อยผ่าน
- รายการอ้างอิง staff ด้วยชื่อที่แสดงในแอปตามที่บันทึกไว้ ถ้ามีการเปลี่ยนชื่อ staff ต้องแก้รายการไม่ว่างที่มีอยู่ด้วยมือ (ไม่ย้ายให้อัตโนมัติ)
